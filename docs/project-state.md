# setsail — project state

Factual capability inventory for Wind Waker HD on Linux. Epic intent is in
`docs/project-goals.md`. Every item is `verified`, `partial`, `blocked`, or `missing`.

**Current focus.** ST-60 -- the objects three frames cannot verify, and the uneven halves of a tick
(ST-PERF). The work is in `wiiuport`; this inventory points at its evidence.

## Comparison baseline

**Baseline: playing Wind Waker HD in upstream Cemu.** A player installs the Cemu
AppImage, adds their WUX to a game list, optionally installs community graphic packs
(`WindWakerHD_Resolution`, `_Contrasty`, `_Shadows`, `_NoSSAO`, `_LODBias`,
`_Anisotropic`, `_RemoveHUD`, `_PictoBox`, `_IntelFixes`, `_FPSSlowdownFix`), and plays
at the title's 30 Hz presentation rate. No 60 fps pack exists for this title. Each item
below states its difference from that baseline.

| ID | Capability (delta from baseline) | State | Evidence / exact gap |
|---|---|---|---|
| ST-BOOT | Title boots to in-game control through our source-built runtime | verified | The runtime is built on this machine from the pinned fork with Clang and Ninja (`wiiuport` `tools/build_runtime.py`, its ST-BUILD) and boots the player's WUX to Outset Island from their save (`wiiuport` ST-HEADLESS-GAME). Control is reached and driven: `POST /input` sticks walk Link along fixed routes through the village and into the surf, and turn the camera, which every interpolation measurement in `wiiuport` ST-OBJECTS rests on; a gamepad is mapped automatically for a player (`wiiuport` ST-PAD). A new game without a save stops at the name-entry keyboard for a driven run only; a player types there. |
| ST-IDENT | Title identity is validated from the player's file before it is accepted | verified | The launcher always tells the runtime which title this product runs (`RuntimeCheckout.launch_command` passes `--title-id 0005000010143500`, `gamefile.TITLE_ID`, `tests/test_launch_command.py`), and the runtime reads the disc's own metadata and refuses any other title in its setup screen and at launch (`wiiuport` ST-SETUP, `shell/TitleIdentity`). Measured on the player's WUX: told another ID it refused with "this disc holds THE LEGEND OF ZELDA The Wind Waker HD (0005000010143500), not the game this product runs", and told this one it ran it. The revision is not pinned: the disc's base version runs unless the player has installed an update, and nothing here depends on it, since the interpolation finds its transforms by what they do rather than at recorded addresses (`wiiuport` ST-CAMERA). |
| ST-CAMERA | Camera transform recovered from the guest's submitted render state | verified | Identified by value in `docs/render-state.md`: a 3x4 (3x3 rotation, translation in the fourth column) carried by 71 of 194 shaders in one frame, each at its own offset. Row norms 1.00000, row dot products 1e-8, constant across every draw of a frame in shaders drawn up to 123 times, translation moving ~2140 units/frame with under 2% step variation. Sharing across unrelated shaders is the discriminator; the other two properties alone do not separate a camera from a moving object. Found by `wiiuport/tools/find_camera.py` from a capture at frame 300. Bounded by one scene and four frames, with no input driven -- offsets are per-shader and must be found at runtime, never read from a table. |
| ST-ACTORS | Actor transforms recovered with stable identity across ticks | partial | The title double-buffers its uniform blocks, so a draw's shader and block addresses identify an object two frames apart; `wiiuport`'s `interp::ObjectPlanner` pairs each object with its draw one frame back by where its own moved values pass through, finding it by values where the blocks name another object, and treats values every draw of a shader holds -- the view -- as frame state rather than identity. Evidence and gaps: `wiiuport` ST-OBJECTS. |
| ST-60 | Presents at 60 Hz with interpolated frames from blended transforms | partial | The runtime presents an in-between frame before every guest swap with the camera and each object blended by its own identity; state and evidence live in `wiiuport` ST-60 and ST-OBJECTS. Live, walking: 792 in-between frames for 798 title frames, the title keeping 98.3% of its rate over paired windows. Gaps are listed there: objects whose identity three frames cannot verify (5.6% of a census, mostly the sea grid's edge coming into view) are drawn un-blended and counted; the HUD is keyed by draw order; effects drawn without uniform blocks are not blended. Geometry the title rewrites on the CPU each frame -- skinned characters, effects -- has its vertices blended from the object's partner in N-1 (324,937 draws over 650 ticks walking, the title keeping 100.0% of its rate over paired windows); a character held still in its uniforms but animated in its vertices still steps at 30 Hz, and the vertex blend adds 4.5 ms a tick to the in-between frame. |
| ST-60-EVIDENCE | Interpolation proven by counters with denominators and code-diffed captures | partial | `wiiuport`'s `tools/continuous_run.py` reports ticks, in-between frames, skips by reason, objects by outcome and by shader, and fails a run where interpolation never fired (`wiiuport` ST-COUNTERS). The between check is on the values drawn; `wiiuport`'s `tools/wiiuport/neighbour_check.py` captures the title's frame, the next in-between frame and the title's frame after it, and requires by code that the in-between image differs from both and is nearer each than they are to each other; its failures are what locate the remaining surf defect (`wiiuport` ST-OBJECTS). |
| ST-PERF | 60 Hz sustained, frame-time percentiles published with the tested hardware | verified | Tested on an AMD Ryzen 7 5700X, 16 GB, AMD Radeon RX 6700 XT (RADV), presenting offscreen at 3840x2160 60 Hz, a player's 4K display, with every blend on (`wiiuport` `tools/session.py --size 3840x2160`, `GET /interpolation`). Over four 8 s windows in the village -- standing, turning, walking, walking while turning -- the title ran at 29.9 to 30.0 ticks a second and every tick had its in-between frame (959 of 959). Frames reached the screen 16.7 ms apart at p50, p95 and p99 in all four, as the presentation engine reported them (first pixel out); the longest gap was one 33.3 ms interval walking while turning. The two presents of a tick are handed over unevenly (p50 8.7 to 24.4 ms, p95 up to 33.6 ms, since the in-between frame is presented just before the title's), and FIFO at 60 Hz spaces them on the display; a display faster than 60 Hz or variable-rate would not, and none has been tested. Gap: a desktop session presents through the compositor, which reports no scan-out times, so the player's own window has not been measured. Baseline: 30 Hz. |
| ST-SAVES | Saves and settings in the OS user-data location, not the checkout | verified | `wiiuport`'s `shell/HostPaths` resolves them before anything is read: data through `SDL_GetPrefPath` (`XDG_DATA_HOME` on Linux), settings under `XDG_CONFIG_HOME` and caches under `XDG_CACHE_HOME`, each in a `Cemu` folder so an existing Cemu installation's keys and NAND are the player's; a `portable` folder beside the executable keeps everything there instead, for a packaged build. Measured: every offscreen run points the XDG variables into its own scratch directory, and the shell logged settings and data there (8 of 8 runs), never under the checkout or the working directory. Baseline Cemu uses the same `~/.local/share/Cemu`. |
| ST-SETUP | No-terminal first-run setup with a native picker for the player's disc image | verified | The runtime owns it: with no `SETSAIL_GAME`, the launcher starts `wiiuport --title-id 0005000010143500` with no disc (`setsail.launch.prepare`, `tests/test_launch_command.py`), and wiiuport's `shared/setup-ui` screen asks for the disc image once, through SDL3's native picker, and remembers it. Driven with exactly that command line (`wiiuport` `tools/setup_screen.py --title-id 0005000010143500 --refuse-as 000500001010ec00`): with nothing remembered the screen is on the display waiting for a selection, 926 colours drawn; with the disc remembered the title starts without asking; and a record holding a disc of another title than the product runs is refused by name and the player asked again. Baseline requires the player to configure Cemu manually. |
| ST-APPIMAGE | Asset-free Linux AppImage release | verified | `tools/package_appimage.py` has `wiiuport` build its release runtime (`tools/build_release_runtime.py`: a clean copy of the committed checkout, built in a pinned Ubuntu 24.04 container at `/build`, staged as a title-neutral bundle with a `runtime.json` manifest), then makes it this product: a launcher fixing `--product-name "Set Sail" --title-id 0005000010143500`, the desktop entry and an original icon, on the pinned type2 AppImage runtime (checksum-verified). `build/appimage/setsail-x86_64.AppImage` is 26.0 MiB, needs glibc 2.38 or newer, and bundles 3 of the 24 libraries the executable links (libstdc++, libbluetooth, libcap): the runtime no longer builds the wx front end, so GTK, cairo and glib are gone, and SDL loads its Wayland and X11 backends from the host. The C library, GL dispatch, fontconfig, and the display, input and font stack are left to the host, and library families are never split between the two. Extracted, no file names the builder's home (0 matches). No game file or key is in it. The packager starts the package twice and refuses it unless both answer as the runtime does: told to run another title it must refuse by name ('Set Sail runs 0005000010143500, not 00050000101c9400'), and with nothing remembered and no display it must report 'the setup screen would not open' and exit 1 without a crash report (`check_exit`). That second start brings the emulated system up and down, and it refuses the package built before `wiiuport`'s exit fix, whose crash handler turned the abort into exit 1 -- the code alone cannot tell (`tests/test_appimage.py`). Driven through `wiiuport`'s `tools/setup_screen.py --product` (2026-09-24): with nothing remembered it shows the first-run screen headed 'Set Sail', and with a remembered title it starts without asking. On another distribution (2026-09-24), the extracted package in a Debian 13 container (glibc 2.41, Debian's Mesa 25.0.7) given only its render node and a display: on X11 it showed the first-run screen, `/setup` reporting it shown and collecting; with the disc remembered, on a virtual KWin's Wayland socket, it opened 'window open: 1280x720 shown on wayland', rendered on the RX 6700 XT through RADV, reached the title screen, and presented 389 in-between frames for 597 of the title's over 20 s; `POST /quit` then ended it with exit 0 in 0.54 s. (Under Xvfb, which has no DRI3, Mesa hands the product llvmpipe instead; the display, not the package.) The container needs what any desktop has: the host-provided libraries above and the X extensions SDL loads at runtime (libX11-xcb, Xext, Xcursor, Xi, Xfixes, Xrandr, Xss, Xtst). Published as the [v0.1.1 prerelease](https://github.com/SomeoneIsWorking/setsail/releases/tag/v0.1.1) (sha256 c9ee1b36...); v0.1.0 predates the exit fix and the Wayland backend. |
| ST-RUNSH | `./run.sh` provisions from a clean checkout and launches the title | verified | `run.sh` hands to `bootstrap.py`, which resolves the sibling wiiuport checkout, brings its runtime's build up to date on every launch (a no-op build is about 4 s, and a failed build never launches the binary that was there before), and starts `external/cemu/bin/wiiuport --title-id 0005000010143500` with the title if one is given (`setsail.launch.prepare`, `tests/test_bootstrap_refusals.py`). `tools/provision.py` runs the same preparation and stops before the product starts. From a fresh `git clone` of both repositories (wiiuport `--recursive`) into an empty directory, with Clang, it built the runtime and printed the launch command, exit 0, 6 min 47 s from clone to binary with vcpkg's binary cache warm on this machine. The title's first run then asks for the disc image on the runtime's setup screen (ST-SETUP). |
| ST-VERIFIER | Canonical Python verifier with format, tidy, structure, and test gates | verified | `tools/verify.py` runs ruff lint, `ruff format --check`, pytest (39 tests), the `run.sh` shim check and source-size limits: 5 of 5 gates pass, and the format gate is shown failing on a packed file (`tests/test_verify.py`). This project has no C or C++ sources, so `clang-format` and `clang-tidy` have nothing to check here; the runtime's C++ is gated in `wiiuport` (its ST-VERIFIER). |

## Dependencies

`wiiuport` owns the runtime and the title-neutral record/replace/replay mechanism.
This project owns only Wind Waker HD's identity, which submitted state is a camera or an
actor transform, the blend policy, packaging, and the release evidence.
