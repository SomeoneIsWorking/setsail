# setsail — project state

Factual capability inventory for Wind Waker HD on Linux. Epic intent is in
`docs/project-goals.md`. Every item is `verified`, `partial`, `blocked`, or `missing`.

**Current focus.** ST-PAINT is now `verified` -- the guest paint path paints twice a tick at
59.99 a second with the logic held at 30.00, measured on the real disc through the control channel
in adjacent windows, and the player's disc image is never touched. What is left is the blend:
the title's own frame is painted twice, so the picture rate is doubled and the motion is not. The
pose and the identity are located -- the node is the identity, tick N-1's uniform block is still
present when tick N paints in 16 of 16 comparisons, and the pose is per-object rather than global,
measured over 1,035,056 assemblies -- and where the blend is written is not: the view matrix is
excluded from the per-draw uniforms, from the module's `.data`/`.bss` and from `0x15800000`, and
the fourth candidate, written through the registration by `FUN_02786520` across 21,488 addresses,
is the next read. That read is a *range*, taken from the guest block addresses each draw sourced,
not a search. All the state and evidence is in `wiiuport` ST-GUESTPAINT and ST-OBJECTS; the
title's own evidence is in this project's `docs/render-state.md` and the mechanism is in
`wiiuport` `docs/frame-interpolation.md`.

**The host-side statistical lerp is deleted, not deferred.** It identified the camera by
searching shaders for a 3x4 that moved like one, matched each draw's identity across ticks by
uniform-block address and occurrence index, guessed which vertex buffers belonged to the same
object, and re-issued a recorded frame under a guest-state guard's shadow and restore of every
render target. Its evidence was measured and is deleted with it: ST-ACTORS, ST-60 and
ST-60-EVIDENCE are gone from this table, ST-CAMERA's method is replaced by the guest's own names
while the title fact it recorded stays, and ST-PERF drops to `missing` rather than quietly
reusing percentiles that were measured for a different mechanism. **Nothing interpolates until the
blend is built, and this inventory says so rather than leaving it to be assumed.**

## Comparison baseline

**Baseline: playing Wind Waker HD in upstream Cemu.** A player installs the Cemu
AppImage, adds their WUX to a game list, optionally installs community graphic packs
(`WindWakerHD_Resolution`, `_Contrasty`, `_Shadows`, `_NoSSAO`, `_LODBias`,
`_Anisotropic`, `_RemoveHUD`, `_PictoBox`, `_IntelFixes`, `_FPSSlowdownFix`), and plays
at the title's 30 Hz presentation rate. No 60 fps pack exists for this title. Each item
below states its difference from that baseline.

| ID | Capability (delta from baseline) | State | Evidence / exact gap |
|---|---|---|---|
| ST-BOOT | Title boots to in-game control through our source-built runtime | verified | The runtime is built on this machine from the pinned fork with Clang and Ninja (`wiiuport` `tools/build_runtime.py`, its ST-BUILD) and boots the player's WUX to Outset Island from their save (`wiiuport` ST-HEADLESS-GAME). Control is reached and driven: `POST /input` sticks walk Link along fixed routes through the village and into the surf, and turn the camera, which every interpolation measurement in `wiiuport` ST-OBJECTS rests on; a gamepad is mapped automatically for a player (`wiiuport` ST-PAD). A new game without a save stops at the name-entry keyboard for a driven run only; a player types there. |
| ST-PAINT | The title's own display paint path, reached from guest memory, painting twice a tick | verified | **Measured, and it holds.** A stand-in for the display frame is placed in guest memory and routed to by rewriting vtable slot `0xcc`, and the picture rate reaches 60/s from the flip interval alone. The eleven words at `0x0274c264` are lifted verbatim from this disc's image, not hand-derived; the stand-in goes into executable guest memory from `RPLLoader_AllocateTrampolineCodeSpace` and is reached through the title's own vtable, so the display thread runs the title's own frame body twice and re-reads the frame from the title's own vtable. Adjacent 8.00 s windows on the real disc, through the control channel: unmodded 240 and 241 paints = **30.00 and 30.12 a second**; with the stand-in, 480 and 478 = **59.99 and 59.73 a second**. The pass rate is unchanged (240 against 241 passes), so the stand-in adds a paint inside a pass rather than adding a pass. **The earlier blockers are resolved and the resolution is recorded because it was the fault, not the premise.** (1) A host segfault reached through `PPCInterpreterSlim_executeInstruction`, the recompiler's **fallback**, on the display fiber: the first runs were failing because the guest code was not being translated at all, and the fix was in the fork's `GuestCallProbes`, not in the guest. (2) The logic doubled -- one tick per paint, one for one -- which is a real finding and is now held at thirty by a gate installed in the logic path at `0x025d42ec`: 30.0 calls a second in, 15.0 ticks a second out over 3.0 s, against the host probe's 90 calls. Tick rate over 8.00 s windows: unmodded 241 paints / 241 tick calls / 120 ticks run; with the stand-in, window 1 at 474 / 474 / 237 = 29.62 a second, **below the 29.9-30.0 band and reported as a failure**, window 2 at 480 / 480 / 240 = **30.00 a second, inside the band**. The `display+0x74 ^= 2` toggle was read at run time through a probe on `0x0274c264` that receives the display pointer in r3; the null-interpolation discriminator now runs against this path instead of a replay, and two consecutive presents differ by 53,634 and 52,911 of 6,220,800 bytes (0.86% and 0.85%) with largest delta 3 and every differing byte within 4, against 32.45% and 34.90% with deltas 164 and 221 for a genuinely different frame. **The player's disc is never touched: the stand-in is written to guest memory at link time and the WUX on disk is read-only input.** What this row does not claim: the picture is the title's own frame twice over, so nothing *moves* at 60 Hz until the blend is built -- ST-60. |
| ST-IDENT | Title identity is validated from the player's file before it is accepted | verified | The launcher always tells the runtime which title this product runs (`RuntimeCheckout.launch_command` passes `--title-id 0005000010143500`, `gamefile.TITLE_ID`, `tests/test_launch_command.py`), and the runtime reads the disc's own metadata and refuses any other title in its setup screen and at launch (`wiiuport` ST-SETUP, `shell/TitleIdentity`). Measured on the player's WUX: told another ID it refused with "this disc holds THE LEGEND OF ZELDA The Wind Waker HD (0005000010143500), not the game this product runs", and told this one it ran it. The revision is not pinned: the disc's base version runs unless the player has installed an update, and nothing here depends on it, since the interpolation finds its transforms by what they do rather than at recorded addresses (`wiiuport` ST-CAMERA). |
| ST-CAMERA | The title names its own camera transform, and it is read from the guest's memory | verified | **The title carries the name itself**, in a flat NUL-terminated table in the module's data area: `cWorldViewMatrix[0]` at `0x10163bb4` (91 of 96 words non-zero) and `cWorldViewProjectionMatrix[0]` at `0x10163d00` (78 of 96), followed by `uBlurOffset`, `uOneMinusNearDivFar` and `cToyCam_Saturation1`. Both addresses are confirmed two ways that agree: read from the running guest through `GET /memory`, and computed from the ELF as `0x10000000 + (0xa5c3f4 - 0x8f8840)`. This **replaces the earlier method** -- a 3x4 carried by 71 of 194 shaders in one frame, found by sharing across unrelated shaders and by how it moved -- and it replaces it because the host was guessing at something the guest already says. **It also withdrew a long-standing blocker in the direction it pointed:** the concern that the running guest's memory is not shown to be the disc image's is now answered, since the names come from the image's own module and the running guest reads at the same addresses. `docs/render-state.md` carries the full identification. |
| ST-PERF | 60 Hz sustained, frame-time percentiles published with the tested hardware | missing | **No performance evidence exists for the mechanism that is shipping, and the evidence that existed was measured for the one that was deleted.** The retired host-side lerp was measured on an AMD Ryzen 7 5700X, 16 GB, AMD Radeon RX 6700 XT (RADV), offscreen at 3840x2160 60 Hz, with its interpolation on -- percentiles, the title's rate over paired windows, the cost of blending the vertices. That evidence is deleted with the mechanism it measured (`wiiuport` ST-60, ST-SHADOW) and is **not** carried over to the guest paint path, because it says nothing about it. What is measured for the paint path is the picture rate and the logic rate, not frame-time percentiles: 59.99 paints a second with the logic held at 30.00 (`wiiuport` ST-GUESTPAINT). **Exact gap: no frame-time percentile, no sustained-load window and no host has been reported for the guest paint path, and none can be until the blend exists** -- a percentile of two identical paints measures the flip, not the work. |
| ST-SAVES | Saves and settings in the OS user-data location, not the checkout | verified | `wiiuport`'s `shell/HostPaths` resolves them before anything is read: data through `SDL_GetPrefPath` (`XDG_DATA_HOME` on Linux), settings under `XDG_CONFIG_HOME` and caches under `XDG_CACHE_HOME`, each in a `Cemu` folder so an existing Cemu installation's keys and NAND are the player's; a `portable` folder beside the executable keeps everything there instead, for a packaged build. Measured: every offscreen run points the XDG variables into its own scratch directory, and the shell logged settings and data there (8 of 8 runs), never under the checkout or the working directory. Baseline Cemu uses the same `~/.local/share/Cemu`. |

## Dependencies

`wiiuport` owns the runtime and the title-neutral record/replace/replay mechanism.
This project owns only Wind Waker HD's identity, which submitted state is a camera or an
actor transform, the blend policy, packaging, and the release evidence.
